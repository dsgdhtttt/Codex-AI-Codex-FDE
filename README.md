从 0 到 1 交付一个 AI 项目：Codex 行动营实战复盘
参加 Codex 行动营之前，我做过不少 AI Demo，但真正从零到一交付一个完整项目，还是第一次。复盘整个过程，最大的体会是：AI 项目成败不取决于模型多强，而取决于交付闭环是否扎实。从选题、设计、开发到评测、部署，每一步都有坑，也都有方法。

第一阶段：选题与需求澄清。 开营第一天，老师就强调：不要先想“用什么模型”，先想“解决谁的问题”。我们小组最初想做全能助手，结果越聊越散。后来收缩到一个具体场景：帮助运营人员快速生成周报。目标用户明确、痛点高频、结果可验收。我们定义了输入输出、成功指标和边界条件：输入是本周数据表和工作记录，输出是结构化周报，要求事实准确、格式统一、可人工修改。需求澄清花了整整两天，但后面开发省了至少一周。方向对了，速度才有意义。

第二阶段：方案设计与任务拆解。 我们决定采用“提示工程 + 工具调用”的轻量方案，而不是一上来就微调。Codex 行动营反复强调：先跑通最小闭环，再逐步加能力。我们把任务拆成五步：数据读取、要点提取、结构生成、语言润色、格式导出。每一步独立可测，失败可回退。同时设计了人工确认节点，关键数据必须由人核对。方案不追求先进，追求稳定和可交付。

第三阶段：开发实现与人机协作。 这是 Codex 发挥价值最大的阶段。我们采用小步快跑：每次只让 AI 生成一个模块，立刻运行验证。上下文工程是关键：提供样例数据、接口约定、命名规范和错误日志。AI 生成后，我们重点审查安全、边界和可维护性，而不是只看能不能跑。遇到问题先定位是需求不清、上下文不足还是逻辑错误，再针对性修改。人负责架构和判断，AI 负责加速实现。

第四阶段：评测与迭代。 项目能不能用，评测说了算。我们建立了小型评测集，覆盖高频场景、边界情况和异常输入。每次修改后跑回归测试，记录准确率、格式合规率和人工修改耗时。发现主要问题不是模型能力，而是数据格式不统一和提示歧义。于是我们增加预处理规则和示例约束，效果明显提升。评测不是走过场，而是把“感觉还行”变成“数据证明可行”。

第五阶段：部署与交付。 上线前我们做了三件事：权限控制、日志监控和回滚方案。运营人员通过简单界面提交数据，系统返回周报草稿，人工确认后导出。部署后第一周，我们每天收集反馈，发现等待时间和格式细节是主要痛点，随后优化了流式输出和模板选项。交付不是发文件，而是让用户真正用起来、愿意继续用。

第六阶段：复盘与沉淀。 项目结束后，我们整理了提示模板、评测用例、踩坑清单和架构决策记录。这些资产让后续类似项目启动时间缩短了一半以上。最大的教训是：前期需求多花时间，后期返工就少；小步验证比一次性大改更稳；人机协同的关键是让人做判断，让 AI 做执行。

从 0 到 1 交付一个 AI 项目，Codex 行动营教给我的不是某个工具，而是一套闭环方法：先窄后宽，先稳后快，先评测后放大，先交付再规模化。模型会更新，框架会过时，但需求澄清、任务拆解、上下文管理、评测迭代和交付运营的能力不会贬值。能坚持跑通闭环，才能真正把 AI 从演示变成生产力。
